Records how far each application query model has processed each aggregate.

public interface IProjectionCheckpointStore

Remarks

The raw and merged layers need no checkpoint: their own document already records the position it was carried to, and a second copy would add a write to the pipeline's hot path plus a value that can disagree with the first. A derived handler has no such document — its query model belongs to the application and may not even live in this database — so without this record its progress is unobservable and a caller cannot wait for it at all.

Written after the handler's own write succeeds, never before. A crash between the two leaves the checkpoint behind, which reports "not yet" and is repaired by the next at-least-once redelivery; the reverse order would report a query model as caught up that never received the event.

Remarks

A shared store rather than an in-process catalogue, and that is the whole point: handlers are registered in the projection worker while the names are asked for in the API host, so a catalogue populated by registration would be empty exactly where it is read and would report every correctly registered projection as unknown.
