Remarks

Polling rather than a broker subscription, on purpose. The pipeline's completion signals are internal addresses with per-aggregate ordering topology: an API host subscribing to them needs its own consumer group or queue per instance, competes with the single active consumer the pipeline relies on, loses every pending wait when it restarts, and still races against notifications that passed before the request arrived. On top of that the merged signal is published only when derived handlers are registered, so in a zero-code deployment there is nothing to subscribe to at all.

What makes polling affordable is that the cost is bounded by the number of waiting requests rather than by throughput, and that one tick serves every wait on the same projection and aggregate type in a single keyed query. A thousand requests waiting on one aggregate produce one query per tick, not a thousand.

Registered as a singleton. The shared poll loop is what the coalescing is built on, and a scoped instance would give every request its own.

Remarks

Timing out, stalling and being shed are returned as outcomes rather than thrown. Cancellation is thrown, because it is the caller withdrawing rather than the system answering.
