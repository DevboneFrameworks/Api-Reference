Remarks

A commit is durable the moment it succeeds, but the read side reaches it later. Every question a caller can ask about that gap — "is my change visible yet", "which token do I send with the next command" — needs a name for the commit, and before this receipt existed the write path returned success and nothing else. The token was reachable only by reading a projection, which is itself subject to the very delay the caller was trying to reason about.

EventSequence is the watermark. It is the last event of this commit and the one position the MongoDB projection pipeline orders by, so "the read model has caught up with my commit" is exactly applied >= EventSequence. Compare with >= and never with ==: delivery is at-least-once and later events may already be applied.

AggregateRevision is not a substitute. One commit may emit several events, so a revision maps to a range of sequences rather than a position, and the projection does not order by it. AggregateConcurrencyToken is not a substitute either: it is opaque and random, so it supports equality and optimistic concurrency but carries no ordering at all.

Remarks

A retry of an ambiguous outcome repeats the request identity, finds the original commit, and writes nothing. The receipt still describes a durable commit and is just as valid to wait on — but a caller counting writes, charging for work, or emitting an integration event on success needs to know that this call was not the one that did it.

Remarks

Used where the commit was performed by someone else and has to be reported faithfully: a repeated request identity whose original commit is being described, and the persistence gateway reporting a duplicate it detected. In those cases the values a fresh commit would have computed describe a commit that never happened, so they must be read back rather than assumed.
