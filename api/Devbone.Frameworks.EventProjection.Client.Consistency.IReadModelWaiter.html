Waits, within a bounded budget, until a framework-standard projection reflects one committed aggregate change.

public interface IReadModelWaiter

Remarks

A convenience over IReadModelConsistencyBarrier, for the case where a caller wants to hold its request briefly and answer with the result. Anything that returns early and lets the client come back — a queued response, a status endpoint, an orchestrator owning its own retry rhythm — should use the barrier check directly instead of blocking here.

This buys read-your-writes for one caller, not consistency for the system. Nobody else's read becomes more consistent, no ordering guarantee changes, and nothing here makes the platform's delivery anything other than at-least-once. It closes exactly one gap: the caller that just wrote something and immediately reads it back.

Use it per request, never as a global mode. Waiting on every write puts a database round trip and the projection's own failure modes on the critical path of the write, which is the opposite of why the read side is separate.

Wait after the command completed, never inside it. The command holds an aggregate lock for its duration, so waiting before it returns adds the projection latency to the lock hold time and to every other writer of that aggregate.

Parameters

barrier ReadModelBarrier

The commit position to wait for.

timeout TimeSpan?

Budget for this wait, or null for the configured default. Values above the configured maximum are clamped, so one caller cannot occupy a slot indefinitely.

cancellationToken CancellationToken

Token that abandons the wait.

Returns

Task<ReadModelWaitResult>

How far the projection had progressed when the wait ended.

Remarks

Timing out, stalling and being shed are returned as outcomes rather than thrown. Cancellation is thrown, because it is the caller withdrawing rather than the system answering.
